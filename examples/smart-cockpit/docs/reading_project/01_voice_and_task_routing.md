# 01 · 前台语音交互与任务分流

用户坐进车里，说“空调调到 24 度”，希望立刻得到反馈；说“整理一下今天的汽车新闻”，又希望助手查资料时，自己仍能继续问路、听音乐。这个模块解决的就是这两种需求如何共存：**保持实时交流，同时把适合后台处理的工作交出去，完成后再接回当前对话。**

理解这一页，需要认识语音模型、工具调用和异步任务之间的关系。先从用户看到的行为理解技术方案。

## 它在项目里的位置

先把 qwen-audio-agent 理解为一套“让语音助手持续交流、持续办事”的运行框架。它提供实时模型接入、会话管理、工具调用、任务调度和结果播报。smart-cockpit 在这些能力上接入座舱界面与业务工具，组成一个可运行的智能座舱示例。

![智能座舱实时语音交互与任务分流：客户端、Gateway、后台 Agent 和共享 Service 的职责与信息流向](assets/voice_and_task_routing.png)

[放大查看架构图](assets/voice_and_task_routing.png)

“前台 Agent”指负责即时交流的模型与工具，不是浏览器页面。它和编排运行时由 Gateway 承载；“后台 Agent”则是另外的任务执行服务。原座舱示例实际启动客户端、Gateway、后台 Agent、Service 四个进程。图中的检索是后台使用的工具能力。

## “空调调到 24 度”是怎样完成的

首先，React 客户端通过浏览器的麦克风接口采集声音，用 Web Audio 处理音频，再通过持续连接的 **WebSocket（图中的 WS）** 发给 Gateway。WS 是双向通道，客户端持续发送音频，Gateway 持续返回回复。这里的 **GCP（Gateway Client Protocol）** 是客户端与框架约定的消息格式，用来统一传递音频、文字、任务事件和播放回执。

Gateway 再把音频交给实时语音模型。示例默认使用 **Qwen Audio 3.0 Realtime Plus**，能够接收音频或文字，输出回复音频和文字，并提出工具调用。项目接入的是现成模型服务；采音、传输、会话和播放链路由客户端与框架配合完成。持续的双向音频传输，加上话轮检测与打断处理，让用户能连续交流，在助手说话时插话。

模型理解“调到 24 度”后，提出一个带参数的温控工具请求。这里的 **Function Calling（工具调用）** 可以理解为：模型把自然语言变成“调用哪项能力、传什么参数”，实际操作交给程序。工具的描述告诉模型什么时候使用它，参数结构告诉模型温度、区域等信息应怎样填写。

接下来，框架通过 **MCP（Model Context Protocol）** 调用 Service 提供的工具。MCP 统一了工具的发现和调用方式，业务代码仍由 Service 实现。Service 检查温度范围等业务条件，更新座舱状态，再返回实际执行结果；前台模型据此组织语音回复。模型提出请求、程序执行、结果返回模型，这就形成了工具调用的闭环。

与此同时，Service 通过 **SSE（服务器向浏览器持续推送事件）** 把状态变化发给客户端，空调面板随之更新。因此，语音回答和界面显示来自同一次业务执行。当前车控是演示状态的修改，尚未接入真实车辆控制接口；这个闭环体现的是语音意图到业务执行、再到界面反馈的完整方案。

## “整理汽车新闻”为什么不会挡住继续聊天

检索新闻需要搜索、阅读网页、整理内容，耗时和步骤都不固定。前台会把用户的目标与必要约束交给框架的异步任务能力。框架建立任务后先返回受理信息，再通过 **A2A（Agent-to-Agent）** 与座舱后台 Agent 通信。这里 A2A 连接的是任务执行者，MCP 连接的是具体业务工具，两者承担不同职责。

后台 Agent 使用另一个模型——示例默认是 **Qwen3.8-Flash**——决定搜索什么、阅读哪些网页、何时总结。前台的实时语音会话继续运行，用户还能聊天或调用前台工具。其关键是**任务提交后无需等待最终结果，工作进度和完成结果通过事件回传**。

后台完成后，框架把结果送回当前对话，并根据当前交互状态安排播报，避免和正在进行的交流抢话。客户端还会上报播放开始、结束或取消等回执，使框架能够区分“任务做完了”和“结果播报完成了”。新闻任务可以保留完整文字报告，语音只介绍简短摘要。

前后台的分工由座舱的领域配置决定：默认车控、导航、音乐、天气和自定义技能走前台，闪购走后台，新闻研究使用后台检索能力。同一业务领域一次只暴露给其中一侧。工具目录限制模型能调用哪些能力，工具描述引导模型怎样选择；这些业务规则由程序执行和校验。

一句话包含多个意图，也可以分别处理。例如“空调调到 24 度，再整理今天的汽车新闻”，空调仍走前台直接执行，新闻交给后台。这样既保留即时操作的反馈速度，也允许较长的工作继续推进。

## 框架提供了什么，座舱项目实现了什么

| 部分 | 提供的能力 | 在座舱中怎样使用 |
|---|---|---|
| qwen-audio-agent 框架 | 实时模型适配、客户端协议、前台工具执行、异步任务生命周期与结果投递 | 座舱 Gateway 通过公开接口装配并复用这些能力 |
| 座舱客户端与 Gateway 配置 | 浏览器音频交互、座舱界面、人设、领域分流与后台委派说明 | 定义用户怎样交互，以及前台可以直接做哪些事 |
| 座舱 Service 与后台 Agent | 座舱工具、业务规则、共享状态，以及后台模型执行循环 | Service 落地实际操作；后台 Agent 完成闪购或新闻研究等任务 |

这个模块体现的技术取舍是：高频交互尽量通过前台工具缩短执行路径；耗时工作通过异步任务维持对话连续性；前后台使用同一份业务状态，界面通过事件获得执行后的事实。场景开发主要落在客户端、配置、业务工具和后台执行逻辑上，框架承担通用的语音与编排能力。

## 放进简历或面试时，怎样表达

项目方案可以概括为：

> 基于 qwen-audio-agent 构建智能座舱语音交互方案，结合 Realtime 语音模型、MCP 业务工具和 A2A 后台 Agent，实现前台车控等直接操作、后台任务异步执行与结果回流，并通过统一业务状态和 SSE 推送同步座舱界面。

这句话描述的是项目方案。个人经历中，再根据自己实际完成的工作选择“接入、配置、实现、扩展、验证”等动词，并补充具体模块。例如确实调整过工具分流，就讲调整了哪些领域、为什么调整、如何验证；确实实现过业务工具，就讲参数设计、业务校验和状态同步。模型能力、框架能力与个人完成的工作都能由此讲清楚。

如果面试官追问“为什么需要前台和后台”，可以沿上面的两个场景回答：调空调需要即时反馈，新闻整理需要多步检索；前者直接调用工具，后者先建立异步任务；后台工作期间实时会话继续，结果回来后由框架安排呈现。理解到这里，已经能解释这个模块的需求、架构、实现技术与设计理由。
