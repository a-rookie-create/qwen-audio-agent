## 2. 讲义补充：用 Python 区分“职责”和“进程”

你可以把一个 Python 应用拆成“对话服务”“任务管理服务”“外部执行客户端”三个对象。这是在划分职责；它们可能都在一个 Python 进程里，也可能通过网络协作。**对象或模块的数量，不决定进程的数量。** 这是原文“三个逻辑组件，不要求分别部署成三个进程”最需要理解的一点。

| 原文中的概念 | 可借助的 Python 理解（teaching） | 类比到这里就停 |
| --- | --- | --- |
| 前台 Agent | 带有模型连接、提示词、上下文和可用工具的对话服务 | 它包含模型推理能力，不是某个界面，也不只是一次 API 调用 |
| 编排运行时 | 管理任务状态、调度、权限与通知的服务对象集合 | “编排”由代码处理，不因此多出一个负责推理的模型 |
| 后台 Agent | 经接口调用的办事服务或受管子进程 | 后台内部模型、工具与 Session 由后台自身及 Adapter 管理 |
| Gateway | 创建这些服务、连接依赖并提供网络入口的宿主，类似 `create_app()` 装配后的服务 | 它描述服务运行形态，不是第四个同级 Agent |
| 客户端 | 负责输入、收音、播放和展示的界面或设备程序 | 客户端不是前台 Agent，手机连接也不代表后台工作在手机执行 |

把这张对照表与[架构总览](../architecture/overview.zh.md#核心逻辑架构)放在一起读；职责的完整边界以原文为准。

## 3. 把三份文档接起来

README 解释**为什么做这个项目**；架构总览解释**靠哪些职责协作实现**；基本概念解释**用户配置和使用时看到的名称**。三份文档讨论的是同一系统的不同视角。

原文的“仅前台模式”说明后台是按需接入的能力。再结合[对话指南](../guides/conversation.zh.md)和[详细架构的实时边界](../architecture/deep-dive.zh.md#3-实时边界)，你会发现请求有三种路径：直接交流、使用可用的前台工具、提交需要后台能力的工作。阅读后面各讲时，先判断自己正在追哪种路径。

另一个易混点是“协议”和“接口”。Python 对象之间可以依靠同名方法协作；两个程序之间则需要约定传输消息。原文的 `BackendPort` 属于内部接口边界，GCP 属于客户端通信协议，Realtime Provider 负责接入实时模型服务。它们各管一条连接，名称里都有“接口”也不能互换。返回[原文“接口边界”](../architecture/overview.zh.md#接口边界)确认三条边界。
